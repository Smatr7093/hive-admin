# Hosting this for your team

## First, decide which thing you are hosting

They are not the same job.

| | **A demo** | **The real console** |
|---|---|---|
| Data | Seeded fixtures, `ADMIN_DATA_DRIVER=memory` | Real KYC documents, PAN numbers, bank accounts |
| Purpose | Your team clicks through and gives feedback | Ops actually runs on it |
| Prerequisites | None | Pen test, IP allowlist, break-glass procedure, the §15 dependencies |
| Time | ~20 minutes | A planned rollout |

This document is mostly about **A**, which is what "share it with my team" almost
always means. The real deployment is at the bottom, and it is gated on things
that are not code — the PRD is right that Phase 1 ships nothing useful and is
non-negotiable.

---

## Before you share the URL — three things

**1. Change the password.** Every seeded account uses `ADMIN_SEED_PASSWORD`,
which defaults to a value published in this repository's README. On localhost
that is convenient. On a URL your team can reach, it is a public login to a
Super Admin account. Set it to something else and the server prints a warning if
you forget.

**2. Leave 2FA on.** `ADMIN_DEMO_SKIP_MFA=1` is in `server/.env` for local
convenience, and the server **refuses to start** with it set and
`NODE_ENV=production` — which every platform below sets for you. That is
deliberate. Give your team the shared TOTP secret instead; they enrol once.

**3. Consider the IP allowlist.** `ADMIN_IP_ALLOWLIST` (AR-07) takes IPs, CIDR
ranges, or prefixes ending in `*`. If your team works from one office or a VPN,
setting it means a leaked URL is not a leaked console. Off by default.

## Option A — show it to a few people right now (10 minutes, temporary)

A tunnel from the machine already running it. No hosting account, no deploy, and
it dies when you close the terminal — which is the right lifetime for "can you
look at this on our call".

```bash
winget install --id Cloudflare.cloudflared
```

Run both servers as you do now, then in two more terminals:

```bash
cloudflared tunnel --url http://localhost:4000
```

```bash
cloudflared tunnel --url http://localhost:3100
```

Each prints a `https://something.trycloudflare.com` URL. Two things must then
line up, or you get an unexplained CORS failure:

```bash
# server/.env — the console's tunnel URL
ADMIN_CONSOLE_ORIGIN=https://<console>.trycloudflare.com

# web/.env.local — the API's tunnel URL
NEXT_PUBLIC_ADMIN_API=https://<api>.trycloudflare.com
```

Restart the API, and **rebuild the console** — `NEXT_PUBLIC_ADMIN_API` is
compiled into the bundle and into the CSP `connect-src`, so a restart is not
enough:

```bash
cd web && npm run build && npm start
```

Share the console URL. Your machine is serving it, so it works only while your
laptop is awake and the terminal is open.

> Tunnel URLs are public and unguessable rather than private. Change the seed
> password first, and prefer this for a live walkthrough over leaving it up.

## Option B — a permanent demo URL (~20 minutes) — recommended

Render, both services from `deploy/render.yaml`. One platform, one blueprint,
Docker builds already written.

### 1. Push to GitHub

Render deploys from a repository. `.gitignore` already excludes `.env`, and
`server/.env` is local demo config with no real secret in it — but check before
you push:

```bash
cd "C:\Users\Naveen\Downloads\Admin Dashboard"
git init
git add -A
git status          # confirm no .env, no node_modules, no .aab
git commit -m "Hive admin dashboard v2.1"
git remote add origin git@github.com:<your-org>/hive-admin.git
git push -u origin main
```

Make the repository **private**. It contains the security documentation, the
findings against `bond-srv`, and the shape of your data model.

### 2. Generate the two secrets and a shared TOTP secret

```bash
node -e "console.log('ADMIN_SEED_PASSWORD =', require('crypto').randomBytes(9).toString('base64url') + '!aA9')"
```

```bash
cd server && node -e "console.log('ADMIN_DEMO_TOTP_SECRET =', require('./lib/crypto').generateTotpSecret())"
```

`ADMIN_JWT_SECRET` and `ADMIN_HASH_PEPPER` are generated by Render itself
(`generateValue: true` in the blueprint) — you never handle them.

### 3. Create the blueprint

Render dashboard → **New** → **Blueprint** → pick the repository. It reads
`deploy/render.yaml` and creates `hive-admin-api` and `hive-admin-console`.

**The first deploy will not work, and that is expected.** Each service needs the
other's URL, and those URLs do not exist until Render has created them.

### 4. Fill in the four values, then redeploy

Render assigns URLs like `https://hive-admin-api.onrender.com`. Set:

On **hive-admin-api** → Environment:

| Key | Value |
|---|---|
| `ADMIN_CONSOLE_ORIGIN` | the **console** URL, with `https://`, no trailing slash |
| `ADMIN_SEED_PASSWORD` | the password from step 2 |
| `ADMIN_DEMO_TOTP_SECRET` | the secret from step 2 |
| `ADMIN_IP_ALLOWLIST` | optional — your office IP or CIDR |

On **hive-admin-console** → Environment:

| Key | Value |
|---|---|
| `NEXT_PUBLIC_ADMIN_API` | the **API** URL, with `https://`, no trailing slash |

Then redeploy **both**. The console must be *rebuilt*, not restarted — that
variable is compiled into its bundle and its CSP.

> The scheme matters. `hive-admin-console.onrender.com` without `https://` will
> not match the browser's `Origin` header, and you will get a CORS error that
> looks like a code problem.

### 5. Check it

```bash
curl https://hive-admin-api.onrender.com/admin/healthz
# {"status":"ok","surface":"admin"}
```

Then open the console URL. You should get the sign-in form, and the red
"2FA disabled" banner should **not** appear — if it does, something is wrong,
because `NODE_ENV=production` should have prevented the service from starting at
all.

### 6. Give your team access

Send, via a password manager rather than Slack or email:

- the console URL
- `ADMIN_SEED_PASSWORD`
- `ADMIN_DEMO_TOTP_SECRET` — each person adds it to Google Authenticator once

Suggest they sign in as `support@tryhive.in` as well as `naveen@tryhive.in`. The
difference in what the two can see is the clearest demonstration of §4, and it
is the thing reviewers most often miss.

### What to expect from a memory-driver demo

- **Data resets on every restart and every deploy.** Approvals and decisions
  your team makes will disappear. That is usually fine for review — say so up
  front, or they will report it as a bug.
- **One instance only.** Sessions live in the same in-memory store, so a second
  replica would reject tokens minted by the first. `numInstances: 1` is set in
  the blueprint; do not raise it without switching to DynamoDB.
- **Free tier sleeps** after 15 minutes idle and takes ~50 seconds to wake. The
  first person in each morning will think it is broken. The blueprint specifies
  `starter` ($7/service/month) for this reason. Drop to `free` if the wake delay
  is acceptable.

## Option B2 — Vercel

Vercel is the natural home for the console. The API is the part that needs a
decision, and it is worth understanding why before you start.

### Why the API is the awkward half

Vercel runs serverless functions: each request may be served by a different
instance, and instances are discarded between requests. The `memory` data driver
keeps **admin sessions** in process memory. So on Vercel with the memory driver,
the invocation that mints a session and the next request that validates it are
usually different processes — and the second one finds no session.

The symptom is that everyone signs in successfully and is immediately signed out
again, which reads like a bug in the auth code rather than a hosting mismatch.
`server/api/index.js` therefore **refuses to start** unless
`ADMIN_DATA_DRIVER=dynamodb`, so you get a clear error at deploy time instead of
a confusing one later.

That leaves two shapes:

| | Console | API | Needs AWS? |
|---|---|---|---|
| **B2a** (simplest) | Vercel | Render / Railway / Fly | No |
| **B2b** (all Vercel) | Vercel | Vercel + DynamoDB | Yes |

---

### B2a — console on Vercel, API on Render ★ recommended

No AWS, two platforms, about twenty minutes. Follow the order below; each step
produces something the next one needs, so skipping ahead means a failed deploy.

#### 1. Push to a private GitHub repository

```bash
cd "C:\Users\Naveen\Downloads\Admin Dashboard"
git init
git add -A
git status          # confirm: no .env, no node_modules, no .zip, no .aab
git commit -m "Hive admin dashboard v2.1"
git remote add origin git@github.com:<your-org>/hive-admin.git
git push -u origin main
```

**Private.** It contains the security documentation and the findings against
`bond-srv`.

#### 2. Generate the two values you will need

```bash
cd server
node -e "console.log('ADMIN_SEED_PASSWORD    =', require('crypto').randomBytes(9).toString('base64url') + '!aA9')"
node -e "console.log('ADMIN_DEMO_TOTP_SECRET =', require('./lib/crypto').generateTotpSecret())"
```

Keep both somewhere you can paste from twice. `ADMIN_JWT_SECRET` and
`ADMIN_HASH_PEPPER` are generated by Render itself — you never handle them.

#### 3. Deploy the API to Render

Render → **New** → **Blueprint** → select the repository. It reads
`deploy/render.yaml` and creates one service, `hive-admin-api`.

It will ask for the values marked `sync: false`. Set:

| Key | Value |
|---|---|
| `ADMIN_SEED_PASSWORD` | from step 2 |
| `ADMIN_DEMO_TOTP_SECRET` | from step 2 |
| `ADMIN_CONSOLE_ORIGIN` | **leave blank for now** |
| `ADMIN_IP_ALLOWLIST` | optional — your office IP or CIDR |

Wait for the build, then confirm it is alive:

```bash
curl https://hive-admin-api.onrender.com/admin/healthz
# {"status":"ok","surface":"admin"}
```

Copy that URL.

#### 4. Deploy the console to Vercel

Vercel → **Add New** → **Project** → import the same repository.

- **Root Directory: `web`** ← the one setting people miss. Vercel then detects
  Next.js on its own; leave the build and output settings alone.
- **Environment Variables:**

  | Key | Value |
  |---|---|
  | `NEXT_PUBLIC_ADMIN_API` | the Render URL from step 3, with `https://`, no trailing slash |

Deploy, and copy the resulting `https://….vercel.app` URL.

#### 5. Close the loop

Back on Render → `hive-admin-api` → Environment → set:

| Key | Value |
|---|---|
| `ADMIN_CONSOLE_ORIGIN` | the Vercel URL from step 4 |

Render restarts the service automatically. That is all this needs — the origin is
read at startup.

**This step is not optional.** It is the CORS allowlist, and until it is set the
API answers `http://localhost:3100` and nothing else. The failure looks like
"Failed to fetch" in the browser with no useful detail.

To confirm it took, check the Render logs — the service prints every origin it
will accept on startup:

```
Console origins allowed (1):
  · https://hive-admin.vercel.app
```

#### 6. Share it

Send via a password manager, not Slack or email:

- the **Vercel** URL (not the Render one — that is the API)
- `ADMIN_SEED_PASSWORD`
- `ADMIN_DEMO_TOTP_SECRET`, which each person adds to their authenticator once

Suggest they sign in as `support@tryhive.in` as well as `naveen@tryhive.in`. The
difference in what those two can see is the clearest demonstration of §4, and the
thing reviewers most often miss.

#### Vercel preview deployments

Every preview gets its own hostname (`…-git-branch-org.vercel.app`), which is a
different origin and will fail CORS against a single allowed origin.

`ADMIN_CONSOLE_ORIGIN` accepts a comma-separated list, so add the ones you
actually want:

```
https://hive-admin.vercel.app,https://hive-admin-git-dev-acme.vercel.app
```

Matching is exact — no wildcards, no patterns, and a trailing slash is tolerated
rather than silently breaking. Every entry is one a person typed on purpose.
**Do not relax this to `*`.** A wildcard on an admin API means any page on the
internet can call it with a victim's token.

### B2b — everything on Vercel

Requires DynamoDB, because the API needs a store that outlives a single
invocation. Use a **sandbox AWS account or a separate table prefix**, never the
production tables.

**1. Create the admin tables**

```bash
cd server
ADMIN_DATA_DRIVER=dynamodb AWS_REGION=ap-south-1 npm run setup:tables
```

**2. Load the demo fixtures**

```bash
ADMIN_DATA_DRIVER=dynamodb \
ADMIN_SEED_PASSWORD="pick-something-not-in-the-readme" \
ADMIN_DEMO_TOTP_SECRET="$(node -e "console.log(require('./lib/crypto').generateTotpSecret())")" \
npm run seed:demo
```

It refuses to run if those tables already contain anything, unless you pass
`--force`. That interlock is there because the tables it writes to include KYC
submissions, and there is no undo.

**3. Deploy the API**

Vercel → Add New → Project → same repository → **Root Directory: `server`**.
`server/vercel.json` routes everything to the function and registers the cron.

Environment variables:

| Key | Value |
|---|---|
| `ADMIN_DATA_DRIVER` | `dynamodb` |
| `ADMIN_JWT_SECRET` | `openssl rand -base64 48` |
| `ADMIN_HASH_PEPPER` | `openssl rand -base64 32` |
| `ADMIN_CONSOLE_ORIGIN` | the console's Vercel URL (set after step 4) |
| `AWS_REGION` | `ap-south-1` |
| `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` | an IAM user scoped to **these tables only** |
| `S3_BUCKET_NAME` | only if you want real KYC document previews |
| `CRON_SECRET` | any long random string — see below |

**4. Deploy the console**

A second Vercel project, **Root Directory: `web`**, with
`NEXT_PUBLIC_ADMIN_API` set to the API project's URL. Then go back and set
`ADMIN_CONSOLE_ORIGIN` on the API project and redeploy it.

**5. The cron**

`server/vercel.json` schedules `/admin/internal/acknowledge-sweep` every 15
minutes. This exists because G-02's 24-hour acknowledgement clock runs whether or
not anyone is awake — on a long-lived process `index.js` handles it with a
5-minute interval, and serverless has no interval. The grievance list endpoint
also sweeps, so this only matters overnight, which is precisely when it matters.

The endpoint is authenticated by `CRON_SECRET` (Vercel sends it as
`Authorization: Bearer`). **Without `CRON_SECRET` set it returns 503 and does
nothing** — it is disabled rather than left open, because an unauthenticated
endpoint that writes to grievance records and sends mail is not something to
leave on a default.

> Cron jobs are limited on Vercel's Hobby plan (one per day). On Hobby, either
> accept that the list endpoint does the sweeping whenever someone opens the
> queue, or run the sweep from anywhere else that can make an authenticated HTTP
> request on a schedule.

**Things to know about the API on Vercel**

- **Cold starts.** The first request after idle pays DynamoDB client setup. Sign-in
  will feel slow occasionally.
- **Rate limiting weakens.** `middleware/rateLimit.js` counts in process memory,
  and serverless instances do not share it — so the effective limit multiplies by
  however many instances are warm. Account lockout after 5 failed passwords still
  works, because that is stored. Do not rely on the rate limiter alone on Vercel.
- **The audit hash chain does more work.** `lib/audit.js` caches the chain tip per
  process; a cold instance rebuilds it by reading the table. Correct, but it grows
  with the log. Fine for a demo, worth revisiting before it holds three years of
  production entries.
- **IP allowlisting still works** (`ADMIN_IP_ALLOWLIST`) — it reads
  `x-forwarded-for`, which Vercel sets.

## Option C — your own VM (Docker)

If you would rather it sat on infrastructure you control, or next to `bond-srv`:

```bash
cd deploy
```

The console is on `:3100`, the API on `:4000`. Put nginx or Caddy in front with

> These Dockerfiles are written but have not been built and run — there is no
> Docker on the machine they were authored on. What they wrap (a production-mode
> `node index.js` and `next build && next start`) has been verified. Budget a few
> minutes for the first build.

## The real deployment — what changes

Not a bigger version of the above. A different set of prerequisites.

**Architecture (§3).**

- The API is the `/admin` namespace on `bond-srv`, not a separate service. Copy
  `server/` to `bond-srv/admin/` and add `app.use("/admin", adminRouter)`. The
  README has the detail.
- The console gets its own subdomain (`admin.tryhive.in`), separate from the
  marketing site (AR-01, AR-09).
- `ADMIN_DATA_DRIVER=dynamodb`. Run `scripts/createAdminTables.js`, or better,
  deploy `server/admin-tables.yaml` — it also provisions the audit-writer IAM
  role that makes L-02 true at the infrastructure layer and not only in code.
- `scripts/createSuperAdmin.js` for the first account. **Create two.** §12
  requires a second Super Admin to reset a lost 2FA device, and the code refuses
  to let a Super Admin reset their own.
- Turn on `ADMIN_IP_ALLOWLIST`. This is the case AR-07 was written for.

**Before it carries real data:**

- The penetration test in §15, covering privilege escalation and IDOR. Run
  `npm run verify:ar03` in CI as well — it is the automated half of that gate.
- **The consumer API must be in scope too.** Several items in
  [`FINDINGS.md`](FINDINGS.md) reach the same KYC documents without touching
  `/admin` at all, and one of them is a complete authentication bypass. A pen
  test scoped to the admin surface alone will certify a hardened front door on a
  building with an open window.
- A written break-glass procedure (open question 1).
- The rate limiter moves to DynamoDB or Redis before you run more than one
  instance — see [`SECURITY.md`](SECURITY.md).
- Decide `ADMIN_KYC_RETENTION_POLICY`. Until it is set, the deletion queue
  refuses to complete any deletion involving KYC records, which is correct but
  will look like a bug to whoever is working that queue.

## Troubleshooting

**Blank page, console full of CSP errors.** `NEXT_PUBLIC_ADMIN_API` was not set
at *build* time. It is compiled into the CSP `connect-src`. Rebuild, don't
restart.

**"Failed to fetch" on sign-in.** `ADMIN_CONSOLE_ORIGIN` on the API does not
exactly match the console's origin. Include `https://`, drop any trailing slash,
and remember `www.` counts as a different origin.

**The API will not start.** Read the first line of the log. It is deliberately
one of: `ADMIN_JWT_SECRET is not set`, `must not equal JWT_SECRET`, `looks like a
placeholder`, or `ADMIN_DEMO_SKIP_MFA=1 with NODE_ENV=production`. Each refuses
to start rather than run in a degraded state.

**Everyone gets signed out constantly.** More than one instance with the memory
driver — including any serverless platform. Sessions live in process memory, so
requests landing on another instance find no session. Pin to one long-lived
instance, or switch to DynamoDB.

**CORS errors only on Vercel preview URLs.** Every preview deployment gets its own
hostname and none of them match `ADMIN_CONSOLE_ORIGIN`. Test against production,
or add the preview origins explicitly. Not a reason to allow `*`.

**The password you set does not work.** If it contains `#` and you put it in a
`.env` file unquoted, dotenv read the `#` as the start of a comment and silently
truncated it. `ADMIN_SEED_PASSWORD="Some!Pass#word"` — with quotes. Platform
environment variables set through a dashboard (Render, Vercel, ECS) do not have
this problem; only `.env` files do.

**Team says their 2FA code is rejected.** Their phone clock has drifted. The
server tolerates ±30 seconds. Also check `ADMIN_DEMO_TOTP_SECRET` is actually set
— without it a fresh secret is generated on every restart, so everyone is
enrolled against a secret that no longer exists.
